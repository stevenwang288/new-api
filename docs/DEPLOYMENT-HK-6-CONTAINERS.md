# 香港 6 容器方案评估

## 现状

服务器：`38.76.169.215`，约 8 GiB 内存、40 GiB 磁盘，磁盘已用约 84%。现有 New API 在 `3000`，依赖 PostgreSQL 和 Redis，另有 Hermes、代理、MCP 和 Nginx 等服务。

## 结论

方案在技术上成立，但当前不适合直接实施。6 个 New API 容器若共享同一数据库和 Redis，可以复用同一个版本和前端资源；但它们不能直接都绑定 `3000`，必须使用反向代理或不同宿主端口。若每个实例还配 dispatcher 和 12 个 lane，内存、CPU、端口及磁盘余量都需要先重新核算。

目前 SSH 仅接受公钥，已知密码方式未建立会话；另外磁盘余量不足以支持无计划的多镜像构建。因此本次只完成公网 HTTP 可达性检查，没有修改香港服务。

## 推荐拓扑

- 1 个 PostgreSQL 和 1 个 Redis，作为共享数据层。
- 6 个 New API 容器，使用同一个已验证镜像版本。
- 由 Nginx 或负载均衡器统一暴露入口。
- dispatcher 按实例或按业务组规划，避免多个实例争用同一组 lane。
- 每个实例使用独立数据挂载、日志限制和健康检查。

## 实施前必须确认

1. 获取可用的 SSH 公钥登录方式，或由用户确认修复 SSH 鉴权。
2. 清理磁盘至至少 30% 可用，并确认 Docker 镜像、日志和数据库增长策略。
3. 明确 6 个实例是共享数据库的高可用副本，还是 6 套完全隔离的 New API。
4. 明确 dispatcher lane 如何分配，以及公网入口是否需要会话粘性。
5. 先做单实例副本和回滚演练，再扩展到 6 个容器。

## 是否需要以后重新构建

不需要每次重新构建。将验证通过的镜像推送到私有镜像仓库，香港及 961 直接按固定版本标签拉取即可。只有代码、前端资源、基础镜像或运行时配置发生变化时才需要重新构建并发布新标签；数据库数据和配置应通过挂载或环境变量持久化。
